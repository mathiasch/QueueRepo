# Security, Governance, Compliance and Legal Requirements for a Multi-Tenant Coding-Agent Platform (as of Nov 2026)

Scope: self-hosted Rust/axum + Postgres web app, separate unprivileged runner, agent CLIs (Claude Code, Codex CLI, Gemini CLI) in rootless Podman (`--cap-drop ALL`, `no-new-privileges`, resource limits), agents with internet access, user-supplied provider credentials and git tokens encrypted with AES-256-GCM under one MASTER_KEY, local accounts + OIDC, shared projects (owner/editor/viewer), Hetzner VPS behind Cloudflare Tunnel, users in CH/EU.

Research caveat: in this session `openai.com`, `developers.openai.com` and `learn.chatgpt.com` were blocked by the network allowlist, so OpenAI primary texts could NOT be fetched; OpenAI findings rely on search-result snippets of the official docs and secondary sources and are marked as such. Several sandbox-vendor and EU AI Act findings come from secondary sources (law-firm notes, vendor comparisons). All legal points are non-binding research notes, not legal advice.

## 1. Threat model for coding agents and mitigations used by leading products

### Takeaway
The core risk is Simon Willison's "lethal trifecta": the agent reads untrusted content (repo files, issues, web pages, dependencies), has private data (code, provider tokens, git tokens) and can communicate externally (open internet). The product as described has all three in every run. Leading products break the trifecta mainly at the network leg (default-deny egress plus domain allowlists, method restriction), plus by removing secrets from the agent phase; none of them claim their firewall is a complete solution.

### Cited Findings
- The "lethal trifecta" (coined 16 June 2025): access to private data + exposure to untrusted content + ability to communicate externally; when combined, prompt injection can make the agent exfiltrate data. Willison's advice is to avoid combining all three, and he rejects guardrail products claiming e.g. 95% block rates as inadequate. Meta's "Agents Rule of Two" (Oct 2025) builds on this. — [Simon Willison, original post](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/) (via search summaries: [HiddenLayer](https://www.hiddenlayer.com/research/the-lethal-trifecta-and-how-to-defend-against-it), [promptfoo](https://www.promptfoo.dev/blog/lethal-trifecta-testing/))
- OWASP Top 10 for Agentic Applications 2026 (published 9 Dec 2025): ASI01 "Agent Goal Hijack" (objective steered via content the agent reads; treat documents, emails, API responses, web pages as untrusted; alert on goal/tool-usage shifts), ASI02 "Tool Misuse and Exploitation" (scope each agent to the functions its task needs; parameter validation). — [OWASP GenAI (via AIGL summary)](https://www.aigl.blog/owasp-top-10-for-agentic-applications-2026/); [guptadeepak ASI01](https://guptadeepak.com/agent-security/threats/asi01/) (secondary; verify against genai.owasp.org)
- OpenAI Codex cloud: two phases. Setup scripts run with full internet access; then control passes to the agent, whose internet access is OFF by default. When enabled, it is per environment, restrictable by a domain allowlist (presets "None" and "Common dependencies") and by HTTP method (only GET, HEAD, OPTIONS). "Secrets configured for cloud environments are available only during setup and are removed before the agent phase starts." OpenAI warns that enabling internet access "exposes your environment to security risks, including exfiltration of code or secrets", citing a GitHub issue that links a malicious script. — [OpenAI Codex docs: Agent internet access](https://developers.openai.com/codex/cloud/agent-internet) (search snippet; page not fetchable here)
- Third-party critique: no documented way to restrict setup-phase egress in Codex cloud. — [WorkOS blog](https://workos.com/blog/agent-sandbox-egress-defaults) (secondary opinion)
- GitHub Copilot coding agent: internet access limited by a firewall by default, with a "recommended allowlist" for dependency downloads; custom allowlist entries per repo (domain incl. subdomains, or scheme+host+path URL). Disabling "will allow Copilot to connect to any host, increasing risks of exfiltration of code or other sensitive information." Blocked requests surface as a warning in the PR. Limitations: the firewall only applies to processes started via the agent's Bash tool, NOT to MCP servers or setup steps, and "should not be considered a comprehensive security solution." — [GitHub Docs: Customize the agent firewall](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-firewall); [Copilot allowlist reference](https://docs.github.com/en/enterprise-cloud@latest/copilot/reference/copilot-allowlist-reference)
- Claude Code sandbox (off by default; built on open-source `@anthropic-ai/sandbox-runtime`): Linux uses bubblewrap for FS isolation, a separate network namespace, socat relay to a local proxy that checks hostnames against `allowedDomains` (starts empty) and `deniedDomains`; UDP/QUIC/ICMP cannot leave; hostnames resolving to local/link-local (incl. 169.254.169.254) are refused; optional seccomp filter blocks Unix sockets. Default reads include credential files like `~/.ssh`, `~/.aws/credentials` unless `sandbox.credentials` deny/mask is set. Writes limited to working dir/temp; `.claude/settings*`, `.mcp.json`, `.bashrc`, `.git/hooks` write-denied. — [Claude Code docs: Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Claude Code sandbox warnings (exact): "By default, when the platform doesn't support the sandbox or the dependency check at startup fails, Claude Code runs commands without sandboxing." / "The built-in proxy enforces the allowlist based on the requested hostname and, by default, does not terminate or inspect TLS traffic." / "The excluded git commands can reach any host, not only the ones in `allowedDomains`." / "An `allowedDomains` entry with no port allows every port on that host." File tools, MCP servers and hooks run outside the sandbox. Recommendation: enforce `enabled`, `failIfUnavailable`, `allowUnsandboxedCommands: false` via managed settings; for unattended/high-risk runs, run Claude Code itself inside a container, VM or the sandbox runtime. — [Claude Code docs: Sandboxing](https://code.claude.com/docs/en/sandboxing)

### Inferences
- With unrestricted internet, any prompt injection in a repo README, issue text, fetched web page or npm/PyPI package post-install script can exfiltrate the workspace, the git token and the provider OAuth token mounted in the container. The single most important missing control is an egress proxy per task: default-deny, per-project domain allowlist (presets like "package registries only"), optional GET/HEAD-only mode for "web research", blocking of RFC1918/link-local/metadata IPs and of the host/runner/Postgres, and logging of all egress for audit.
- Separate phases like Codex: dependency install/setup with registry-only egress and secrets; agent phase with secrets removed and egress restricted. Git push should be done by the runner (outside the container) after the run, so the git token never enters the agent container at all.
- Provider credentials are unavoidable inside the container (the CLI needs them), so treat them as exfiltratable: prefer short-lived tokens, allow only the provider's API hostnames in the allowlist when "no internet" is selected, and give users a one-click revoke/rotate flow.
- Additional expected controls: secret scanning of agent diffs/commits and logs before push (e.g., gitleaks/trufflehog-style) and redaction in stored transcripts; agents produce branches/PRs, never push to protected branches; human approval for merge; read-only mounts for anything outside the workspace; enforce the agents' own permission/sandbox modes via managed config files the agent cannot write.
- Cross-project contamination: workspaces of different tenants must never share a container, volume, UID mapping, or package cache that is writable (cache poisoning).

## 2. Is rootless Podman + cap-drop sufficient, or are microVMs expected?

### Takeaway
Rootless containers reduce the blast radius of a breakout but still share the host kernel; for untrusted, internet-connected, multi-tenant agent code the industry norm in hosted sandboxes is gVisor or Firecracker/Kata microVMs. For a small self-hosted deployment among trusted users, hardened rootless Podman may be acceptable, but a "top-tier multi-tenant" claim realistically needs gVisor (runsc works with Podman) or microVMs.

### Cited Findings
- Standard runc containers expose the full host kernel surface: "Every host-kernel CVE reachable from unprivileged userspace applies." gVisor's Sentry intercepts most syscalls; the paper reports gVisor exposing 84 host syscalls through its filter vs 400+ for runc. The Sentry is itself large; three in-window gVisor CVEs were information-disclosure only. vsock bugs CVE-2024-50264 and CVE-2025-21756 affect runc and also reach microVMs. — [arXiv 2606.08433: AI Code Sandboxes – A Comparative Security Study, Part 1](https://arxiv.org/pdf/2606.08433)
- Rootless mode maps container root to an unprivileged host UID, limiting what a breakout yields, but does not shrink the kernel attack surface; kernel bugs CVE-2024-1086 and CVE-2022-0492 and runc escapes (CVE-2019-5736, "Leaky Vessels") are cited as container-escape examples. — [DEV Community: Linux copy primitive bugs](https://dev.to/kunal_d6a8fea2309e1571ee7/linux-copy-primitive-bugs-keep-breaking-container-security-from-dirty-cow-to-leaky-vessels-2026-hba) (practitioner blog; secondary)
- Vendors: E2B runs each sandbox in a Firecracker microVM with its own guest kernel on KVM (open source, self-hostable); Modal sandboxes use gVisor (optional VM runtime); Daytona is container-based by default with Kata/Sysbox opt-in (sources conflict: another describes Docker + gVisor). — [Upstash: 15 sandbox providers compared 2026](https://upstash.com/blog/ai-agent-sandbox-providers-compared-2026); [LogRocket comparison](https://blog.logrocket.com/comparing-ai-agent-sandbox-platforms-e2b-modal-daytona-and-more/); [Beri.net comparison](https://www.beri.net/article/e2b-vs-modal-vs-daytona-agent-sandbox-pricing-isolation-2026) (all secondary; conflicting on Daytona)
- GitHub Copilot coding agent runs inside the GitHub Actions appliance environment (ephemeral runner VMs); its firewall "only operates within the GitHub Actions appliance environment". — [GitHub Docs](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-firewall)
- Anthropic recommends running Claude Code itself inside a container, VM or the sandbox runtime for unattended/high-risk runs, treating its own sandbox as one layer. — [Claude Code docs: Sandboxing](https://code.claude.com/docs/en/sandboxing)

### Inferences
- Current setup (rootless Podman, cap-drop ALL, no-new-privileges, cgroup limits) is a good baseline but missing: (a) a stricter runtime (gVisor `runsc` as OCI runtime for Podman, or Kata/Firecracker); (b) custom seccomp profile, read-only root FS, `--userns=auto` so each task gets a distinct UID range, tmpfs `/tmp` with size limits, disk quotas on workspaces; (c) separate network per task (Podman network with egress only via proxy; no access to host, Postgres, runner API, Cloudflare Tunnel daemon, or other containers); (d) fast kernel patching and Podman/crun updates (VPS kernel is the security boundary); (e) ephemeral containers per task, destroyed after the run.
- Note: Hetzner cloud VPS typically does not expose nested KVM, so Firecracker/Kata may require dedicated (bare-metal) servers; gVisor (ptrace/systrap platform) works without KVM. (Inference; verify with Hetzner docs.)
- If tenants are only one team/organization that trusts each other, document the residual risk; if strangers share one host, kernel-sharing isolation is not industry-standard.

### Gaps
- No primary-source confirmation of OpenAI Codex cloud's or Devin's underlying isolation technology (container vs microVM) found this session.
- Hetzner nested virtualization support not verified.

## 3. Secrets management

### Takeaway
A single static MASTER_KEY with AES-256-GCM is a reasonable start but lacks the properties reviewers expect: envelope encryption (per-tenant/per-secret data keys wrapped by a KEK held outside the DB host, e.g., KMS/Vault/HSM or at least a separate file/TPM), key versioning and rotation, AAD binding, and minimization of where decrypted secrets travel. Subscription OAuth tokens are high-value, refreshable credentials and carry ToS constraints (see section 4).

### Cited Findings
- OpenAI Codex docs: "If you use file-based storage, treat ~/.codex/auth.json like a password: it contains access tokens." For CI with a ChatGPT account: seed `auth.json` through secure storage, let Codex refresh it in place, and persist the updated file between runs; API keys are "the right default for automation because they are simpler to provision and rotate". — [OpenAI Codex docs: Authentication (search snippet)](https://learn.chatgpt.com/docs/auth) (could not fetch directly)
- Copied Codex tokens expire/refresh, breaking automated workflows until regenerated; workspace admins can disable device-code auth, blocking headless login. — [openai/codex issue #3820](https://github.com/openai/codex/issues/3820); [openai/codex issue #9253](https://github.com/openai/codex/issues/9253)
- Codex cloud removes environment secrets before the agent phase. — [OpenAI Codex docs: Agent internet access](https://developers.openai.com/codex/cloud/agent-internet) (search snippet)
- Claude Code sandbox supports `credentials` deny/mask for files and env vars (e.g., `GITHUB_TOKEN`); warning that with default `onExtractNoMatch: warn` "sandboxed commands can read the real file unmasked". — [Claude Code docs: Sandboxing](https://code.claude.com/docs/en/sandboxing)

### Inferences
- Recommended design: per-secret random DEK (AES-256-GCM) wrapped by a versioned KEK; KEK in Vault Transit/OpenBao, a cloud KMS, or at minimum a key file outside Postgres and outside backups; AAD = (tenant_id, secret_id, purpose, key_version) to stop ciphertext swapping between users; `key_version` column and an online re-wrap job for rotation; MASTER_KEY never in env of the web process if only the runner needs decryption (or vice versa); zeroize plaintext in memory (Rust `zeroize`/`secrecy` crates).
- Refreshable OAuth files (auth.json, Gemini oauth_creds.json, Claude credentials) are mutated by the CLI during runs; the runner must write back refreshed tokens re-encrypted, with concurrency control (one run per credential at a time or locking), else tokens get invalidated.
- Git tokens: prefer GitHub App installation tokens / fine-grained PATs with repo scope and expiry; inject only into the runner's push step, not into the agent container.
- Provide: credential last-used timestamps, revoke, expiry warnings, audit events for create/read-for-run/delete; backups encrypted with a different key.

### Gaps
- No vendor-specific guidance found on secure server-side storage of Claude setup-tokens or Gemini OAuth credentials.

## 4. Terms of service: subscription credentials on a self-hosted, automated, multi-user server

### Takeaway (non-binding)
Anthropic (as of its current Claude Code Legal & Compliance page) explicitly allows an end user to sign in to the unmodified Claude Code binary with their own subscription, including where a platform hosts Claude Code, but forbids third-party developers from offering Claude.ai login in their apps, routing requests through Free/Pro/Max/Ultra credentials on behalf of users, or collecting/storing/intermediating Claude.ai credentials or session tokens; hosting Claude Code in a product requires the Commercial Terms. This makes a design where the platform stores users' `claude setup-token` values legally risky. Google states that using Gemini CLI OAuth with third-party software to access the backing services violates its terms and may lead to suspension. OpenAI recommends API keys for automation; ChatGPT login is an "advanced" path for trusted runners; consumer terms prohibit credential sharing and programmatic extraction (not verified from primary text this session).

### Cited Findings
- Anthropic: Claude Code use is subject to Commercial Terms (Team, Enterprise, API) or Consumer Terms (Free, Pro, Max, Ultra). — [Claude Code docs: Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)
- Anthropic, "Can customers offer Claude Code in their products?": "Unless we've mutually agreed otherwise, preinstalling or running Claude Code in your products or services (e.g. in hosted sandboxes or other agent infrastructure) requires agreeing to our Commercial Terms of Service and complying with the conditions below: The Claude Code binary must not be modified. ... customers may not remove, disable, or restrict any authentication method built into it ... Customers may not pay for, resell, or intermediate Claude usage on their end users' behalf. Each end user must authenticate with their own Anthropic API key, Claude subscription plan credentials, or 3P inference provider credential ..." — [Claude Code docs: Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)
- Anthropic, "Authentication and credential use": "OAuth authentication is intended exclusively for purchasers of Claude Free, Pro, Max, Ultra, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications." ... "Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, Max, or Ultra plan credentials on behalf of their users. Moreover, developers may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow." ... "Nor does it prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code as described under Can customers offer Claude Code in their products? above." "Anthropic reserves the right to take measures to enforce these restrictions and may do so without prior notice." — [Claude Code docs: Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)
- Anthropic: "Advertised usage limits for Pro, Max, and Ultra plans assume ordinary, individual usage of Claude Code and the Agent SDK." Agent SDK products should use API key auth. — [Claude Code docs: Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)
- Anthropic Consumer Terms (effective 8 Oct 2025): "You may not share your Account login information, Anthropic API key, or Account credentials with anyone else"; Section 3(7) prohibits accessing the Services "through automated or non-human means, whether through a bot, script, or otherwise", except via an Anthropic API key or where Anthropic "otherwise explicitly permit[s] it". Materials may be used for training unless the user opts out; even with opt-out, used when feedback is given or content is flagged for safety review. — [Anthropic Consumer Terms](https://www.anthropic.com/legal/consumer-terms)
- Google Gemini CLI terms page: terms depend on auth method: Google account (Code Assist for individuals) → Google ToS + Code Assist privacy notice; Google AI Pro/Ultra → Google ToS, Google One Additional ToS, Google Privacy Policy; Standard/Enterprise → Google Cloud ToS; Gemini API key → Gemini API ToS Unpaid vs Paid Services; Vertex AI → Google Cloud Platform Service Terms. Directly accessing "the services powering Gemini CLI" using "third-party software, tools, or services" (example: "using OpenClaw with Gemini CLI OAuth") violates applicable terms and "may be grounds for suspension or termination of your account." — [Gemini CLI docs: Terms of Service and Privacy Notice](https://github.com/google-gemini/gemini-cli/blob/main/docs/resources/tos-privacy.md) (paraphrased by fetch tool; Gemini CLI also contains a `BannedAccountDialog` UI component per repo code search)
- OpenAI Codex: API keys recommended for CI/automation; the ChatGPT-account path is labeled advanced and meant for trusted runners (e.g., enterprise teams on ChatGPT-managed access or users who need ChatGPT/Codex rate limits instead of API billing); headless login via `codex login --device-auth` or copying `~/.codex/auth.json`. — [OpenAI Codex docs: Authentication / Non-interactive mode (search snippets)](https://learn.chatgpt.com/docs/auth)
- OpenAI consumer Terms of Use reportedly prohibit to "automatically or programmatically extract data or Output" (ROW version last updated 5 March 2026); Codex is bundled into ChatGPT plans under the same ChatGPT Terms, business users under the Online Services Agreement. — [ConductAtlas provision record](https://conductatlas.com/platform/openai/openai-terms-of-use/provision/CA-P-078686/no-automated-extraction-of-data-or-output/); [OpenAI community thread](https://community.openai.com/t/building-a-browser-to-codex-bridge-via-codex-mcp-server-tou-clarification-needed/1375345) (secondary; primary text not fetchable)

### Inferences (non-binding)
- Anthropic: a self-hosted instance where each user runs the unmodified `claude` binary with their own subscription is within the explicitly allowed carve-out, but (a) if the operator offers the platform as a product/service to others, Commercial Terms acceptance is required; (b) collecting and storing the user's `claude setup-token` in the platform DB plausibly counts as "collect, store, or intermediate Claude.ai credentials" — safest design: the user completes login through Anthropic's own flow inside their own runner container (e.g., `claude /login` in an interactive terminal session in the container) with the token stored only in that user's container volume, or offer API key / Bedrock / Vertex as the primary path; (c) never let one user's subscription serve another user's project runs (shared projects: run under the triggering user's own credential, never the owner's); (d) high-volume 24/7 queues may conflict with "ordinary, individual usage".
- Google: storing a user's Gemini CLI OAuth creds and running the unmodified Gemini CLI is not the same as "using third-party software with Gemini CLI OAuth", but the boundary is unclear; Gemini API key (paid tier) or Vertex AI is the defensible path for a platform, also because the unpaid tier and consumer accounts have different data-use terms.
- OpenAI: per-user ChatGPT login via device-auth inside the user's runner is in line with documented headless usage; sharing one account across users violates the credential-sharing ban (unverified exact wording this session). API keys or ChatGPT Business/Enterprise are the defensible path.
- Product should show a ToS notice per auth method, default to API-key/enterprise options, and make clear that the operator does not resell usage.

## 5. Enterprise/governance features expected

### Takeaway
Competing agent platforms ship admin-enforced policy (managed settings, firewall allowlists per repo/org, blocked-request reporting), and enterprise buyers expect SSO/SAML+SCIM, MFA/passkeys, granular RBAC, immutable audit logs with export, retention controls and approval gates for risky agent actions. The described product has OIDC and three project roles but no evidence of audit logging, SCIM, MFA, org-level policy or retention settings.

### Cited Findings
- Claude Code recommends centrally enforcing sandbox via managed settings that "Developers can't loosen" and that repository settings can't override; `allowManagedDomainsOnly` for domain lists. — [Claude Code docs: Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Copilot coding agent: admins configure allowlists per repository/organization; blocked requests are reported in the PR with address and command. — [GitHub Docs](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-firewall)
- Codex workspace admins can disable device-code auth for ChatGPT workspaces (an admin control over how agents authenticate). — [openai/codex issue #9253](https://github.com/openai/codex/issues/9253)
- OWASP ASI01 recommends alerting on shifts in goals or tool-usage patterns (monitoring/audit). — [AIGL summary of OWASP Agentic Top 10](https://www.aigl.blog/owasp-top-10-for-agentic-applications-2026/)

### Inferences
- Minimum expected feature list: org/workspace layer above projects; roles incl. org admin, billing, auditor; per-project policies (egress preset, allowed agents/models, max runtime/cost, allowed branches, require human approval before push/PR/merge, allowed MCP servers); policy-as-code (e.g., versioned YAML/OPA/Cedar) with admin override precedence; append-only audit log (logins, MFA changes, role changes, credential add/use/delete, run start/stop, egress blocks, pushes) with export (JSON/SIEM/syslog) and hash-chaining; SSO: OIDC already present, add SAML 2.0 and SCIM 2.0 for enterprise, enforce SSO per org; MFA via TOTP and WebAuthn/passkeys, admin-enforceable; session list/revoke; data retention settings for transcripts/logs/workspaces with automatic deletion; per-user export/deletion (DSAR).

### Gaps
- No primary-source survey of enterprise feature sets of Devin, Cursor background agents or Codex Enterprise admin console was gathered in this session.

## 6. Compliance for CH/EU (non-binding)

### Takeaway
The operator is a controller (and for hosted customers a processor) under Swiss FADP/revDSG and GDPR; existing data protection law applies directly to AI processing per the FDPIC. Key obligations: transparency/privacy notice naming LLM providers and US transfers, DPAs with processors (Hetzner, Cloudflare, and LLM providers when the operator holds the account), transfer mechanism (Swiss-US and EU-US DPF certification or SCCs), records of processing, DPIA where high risk, breach notification, data security. EU AI Act: a coding-agent platform is generally not a high-risk system; Article 50 transparency duties have applied since 2 Aug 2026; high-risk dates postponed by the Digital Omnibus. NIS2 likely only relevant if the operator is a medium/large provider of covered digital services.

### Cited Findings
- FDPIC (Nov 2023, reaffirmed May 2025): the FADP in force since 1 Sept 2023 is directly applicable to AI-supported processing of personal data; requires transparency about purpose, operation and data sources of AI processing; DPIA required in high-risk cases. — [FDPIC: Current data protection legislation is directly applicable to AI](https://www.edoeb.admin.ch/edoeb/en/home/kurzmeldungen/2023/20231109_ki_dsg.html); [FDPIC update 2025](https://edoeb.admin.ch/en/update-current-legislation-directly-applicable-ai); [FDPIC: AI and data protection](https://www.edoeb.admin.ch/en/ai-and-data-protection)
- FDPIC Data Protection Day 2026: users should be able to tell when they deal with AI and how their prompt data may be used. — [FDPIC: Data Protection Day 2026](https://www.edoeb.admin.ch/en/data-protection-day-2026) (via search summary)
- Swiss-U.S. Data Privacy Framework recognized by the Federal Council, effective 15 Sept 2024; transfers rely on it only if the US recipient is certified (check "Active" status and the Swiss-US extension on dataprivacyframework.gov); otherwise Swiss-adapted SCCs plus a transfer assessment. — [Homburger](https://homburger.ch/en/insights/new-swiss-u-s-data-privacy-framework); [EPFL data protection](https://www.epfl.ch/campus/services/data-protection/en/at-last-the-swiss-u-s-data-privacy-framework-dpf-has-arrived)
- EU AI Act Digital Omnibus on AI = Regulation (EU) 2026/1744 (Council approval 29 June 2026, OJ 24 July 2026, in force 27 July 2026): Annex III high-risk obligations moved from 2 Aug 2026 to 2 Dec 2027, Annex I to 2 Aug 2028; Article 50 transparency obligations not postponed (applies from 2 Aug 2026), with a grace period for watermarking of systems already on the market until 2 Dec 2026 (sources differ in detail). — [Orrick, July 2026](https://www.orrick.com/en/Insights/2026/07/EU-AI-Act-Update-Digital-Omnibus-Finalizes-8-Compliance-Changes); [Gibson Dunn](https://www.gibsondunn.com/eu-ai-act-omnibus-agreement-postponed-high-risk-deadlines-and-other-key-changes/); [CSA research note](https://labs.cloudsecurityalliance.org/research/csa-research-note-eu-ai-act-omnibus-vii-deadline-delay-20260/) (secondary; OJ text not checked)
- Anthropic consumer accounts: Materials may be used for training unless opted out. — [Anthropic Consumer Terms](https://www.anthropic.com/legal/consumer-terms)
- Gemini API unpaid vs paid services are governed by different terms (data-use differs). — [Gemini CLI ToS page](https://github.com/google-gemini/gemini-cli/blob/main/docs/resources/tos-privacy.md)

### Inferences (non-binding)
- Statutory references the operator should map (from the legal texts, not re-fetched this session): FADP Art. 7 (privacy by design/default), Art. 8 + Data Protection Ordinance (data security), Art. 9 (processors), Art. 12 (records of processing, with SME exemption), Art. 16-17 (cross-border transfers), Art. 19 (duty to inform), Art. 22 (DPIA), Art. 24 (breach notification to FDPIC "as soon as possible"); GDPR Art. 13/14, 25, 28 (DPA), 30, 32, 33 (72h), 35, 44-49 (transfers); for EU users without EU establishment possibly an EU representative (GDPR Art. 27) and for Swiss operators of EU-facing services the extraterritorial reach of GDPR Art. 3(2). Sources: [FADP on Fedlex](https://www.fedlex.admin.ch/eli/cc/2022/491/en), [GDPR on EUR-Lex](https://eur-lex.europa.eu/eli/reg/2016/679/oj).
- Role split: when users bring their own provider credentials, the user (or their employer) contracts with the LLM provider directly; the operator then does not need a DPA with Anthropic/OpenAI/Google for those runs but must disclose that code and prompts go to the chosen provider (possibly US) under the user's own terms. Consumer subscriptions (Pro/Max, ChatGPT Plus, free Gemini) may permit training use -> companies processing client code or personal data should use commercial/API tiers with DPAs and ZDR where available.
- Repos often contain personal data (commit author emails, customer data in fixtures); agents with web access may send it to arbitrary hosts -> egress control is also a data-protection control (FADP Art. 8 / GDPR Art. 32).
- Hetzner (DE/FI, EU) is adequate for CH; Cloudflare Tunnel means Cloudflare (US) terminates TLS and sees traffic -> needs DPA and DPF/SCC basis, disclosure in privacy notice.
- EU AI Act: the operator is likely a "deployer" (or "provider" if it places its own AI system under its name on the market); coding assistance is not an Annex III high-risk use; Art. 50 duties mainly concern informing people that they interact with AI and marking AI-generated content — relevant e.g. for agent-authored commits/PR comments (label as AI-generated, e.g., commit trailers). Art. 4 AI literacy (in force since Feb 2025) applies to deployers' staff. The Omnibus may have changed Art. 4; not verified.
- NIS2: applies to medium/large entities in listed sectors (cloud computing, managed services providers etc.); a small self-hosted operator is likely below thresholds; Switzerland is not an EU member, but has had a cyberattack reporting obligation for critical infrastructure under the Information Security Act since April 2025 (not verified this session).
- Documentation an operator should hold: privacy notice, records of processing, sub-processor list (Hetzner, Cloudflare, email provider, LLM providers when operator-provided), DPAs, transfer assessments, TOMs document (encryption, isolation, egress, access control, backups), DPIA (agents with internet + client code), incident response and breach notification procedure, retention and deletion concept, ToS/AUP for the platform including prohibited uses, AI transparency statement, vulnerability disclosure policy (security.txt).

## 7. Web app security baseline

### Takeaway
No new sources were gathered for this section within the tool budget; the following is the established baseline (OWASP ASVS / Cheat Sheets) mapped to the stack, labeled as inference.

### Cited Findings
- (None fetched this session.) Reference standards: [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/), [OWASP Cheat Sheet Series](https://cheatsheetseries.owasp.org/).

### Inferences
- CSRF: SameSite=Lax/Strict session cookies plus CSRF tokens or Origin/Sec-Fetch-Site checks on all state-changing axum routes; WebSocket/SSE endpoints for agent terminals must check Origin.
- CSP: strict CSP (nonce-based script-src, no inline, `frame-ancestors 'none'`), since agent output/markdown rendered in the UI is attacker-controllable (prompt injection -> XSS in transcripts/diff viewers); sanitize rendered markdown and ANSI output.
- Headers: HSTS, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, COOP; Cloudflare Tunnel: trust `CF-Connecting-IP` only from the tunnel, lock origin to tunnel only.
- Auth: Argon2id with tuned params; rate limiting and progressive lockout per account and IP (tower-governor or similar), generic error messages; MFA (TOTP, WebAuthn/passkeys); secure account recovery (single-use, short-lived, hashed tokens; re-auth for sensitive actions such as adding credentials or changing email); OIDC: validate `iss`/`aud`/nonce/PKCE, link accounts only on verified email, beware Apple private relay emails.
- Sessions: server-side sessions, rotation on login/privilege change, idle and absolute timeouts, list/revoke, invalidate on password change.
- Authorization: object-level checks on every project/run/credential endpoint (IDOR is the main multi-tenant web risk); viewers must not see secrets or be able to trigger runs that use someone else's credentials.
- Supply chain for the platform itself: `cargo audit`/`cargo deny`, Dependabot/Renovate, container image scanning, signed releases, SBOM (CycloneDX/SPDX) per release, pinned agent CLI versions with checksum verification (relevant given Anthropic's "binary must not be modified" condition).
